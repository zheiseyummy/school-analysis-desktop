# 成绩分析系统开发历程与环境准备（讲解版）

版本：截至 2026-10-08 的 Windows `1.1 beta` 试用版
文档更新日期：2026-10-09
用途：向非技术人员介绍项目怎么做出来、用了哪些技术、如何准备开发环境，以及距离最终版还差什么。

> 先说明结论：目前已经形成可在 Windows 窗口中运行的 `1.1 beta` 试用版，但还不是学校正式验收后的最终版。真实成绩表的全流程验证、高中赋分规则和其他电脑离线验收仍是后续工作。

## 一、先用一分钟讲清这个项目

可以这样介绍：

> 这是一个给个人在 Windows 电脑上使用的成绩分析系统。我们保留了熟悉的网页式操作界面，但把它包装成双击就能打开的桌面窗口。学生、考试和成绩存在本机 SQLite 数据库，不需要部署学校服务器。系统可以维护基础信息、导入考试成绩、做年级班级和个人分析、导出 Excel/PDF 报告，也包含初中综合素质评价。现在完成的是第一代 beta，程序和虚拟数据通过了多轮检查；下一步要用学校正式成绩表和其他 Windows 电脑做实际验收。

## 二、为什么要做单机桌面版

最初的项目形态包含面向多人、服务器部署的通用模块，但实际使用目标已经明确：个人在 Windows 电脑本地使用，不需要多人账号、远程服务器或云数据库。因此开发过程中做了三件事：

1. **留下有用的业务**：保留年级、班级、学生、教师、学科、考试、成绩、学情分析、综合素质评价和数据备份。
2. **去掉不需要的系统部分**：移除首页、登录、权限、JWT、Redis、问卷、错题等与当前目标无关的功能；管理页面按实际工作精简字段。
3. **改为本地运行**：业务数据放进 SQLite，文件和备份留在本机；桌面程序直接打开窗口，不要求用户先手动开浏览器或部署服务器。

这里所说的“没有服务器”，是指不需要远程服务器。桌面程序内部仍会在这台电脑启动一个仅供本机窗口使用的本地服务，这是界面和业务代码之间的通信方式，数据不会因此自动上传互联网。

## 三、从需求到 beta 的开发过程

### 阶段 1：确认要解决的问题

先把需求拆成可验证的流程：基础信息如何关联、考试如何设置、成绩表如何导入、缺考和未选科如何表示、分析结果如何计算、报告如何导出、数据如何备份。需求不清楚的部分单独标为待确认，尤其是各校的成绩模板和高中赋分政策，不能由开发人员凭经验猜规则。

### 阶段 2：梳理并精简原有项目

检查原有页面、接口、数据库表和依赖之间的关系，决定每个模块是保留、改造还是移除。UI 没有全部重做，继续沿用 Vue 3、Element Plus 和 ECharts 的页面体系；重点是把多用户/服务器模式改为单用户本地模式。

### 阶段 3：建立本地数据底座

- 使用 **SQLite** 保存年级、学生、考试、成绩和关系数据。它是一个本地数据库文件，不需要安装数据库服务器。
- 上传文件、备份、导出和日志使用本地目录，不再要求 MySQL、Redis、MinIO 或云存储服务。
- 建立数据库升级版本和升级前备份，避免新版本改变表结构时直接丢失旧数据。
- 学生通过学号、班级和学年关系与考试成绩相连；教师通过“教师—班级—学科”任教关系与教学分析相连。

### 阶段 4：逐步完成业务闭环

开发没有一次性重写全部系统，而是按“录入基础资料→创建考试→导入成绩→核对结果→分析→导出”的顺序逐项推进。

- **基础资料**：年级、班级、学生、教师和学科管理；教师可维护所带班级和任教学科。
- **考试和成绩**：考试可配置学年、学期、适用对象、科目、满分和是否计入总分；成绩导入支持校验、差异预览、确认、批次记录和撤销第一版。
- **成绩状态**：将正常 0 分、缺考和未选科区分开。真实 0 分是有效分数，不能与空白或缺考混为一谈。
- **分析报告**：包括年级、班级、学生、学科、教师任教班级对比、历次考试、进退步、临界生和偏科等第一版分析；学生个人报告支持 Excel 和 PDF，批量时仍为每个学生生成独立文件。
- **综合素质评价**：支持六学期、五个维度、缺失确认和教师最终确认。确认存在缺失学期的学生标记为 `N/A`，不参加 A/B/C 比例和排名；最终人数由最后一个学期名单确定。
- **高中选科**：实现了 `3+1+2` 选科组合信息框架。赋分算法目前暂停，等学校提供具体政策、计算群体和边界规则后再开发。

### 阶段 5：把网页式业务装进 Windows 窗口

最终交付采用 Tauri 桌面窗口：

1. 前端生成静态网页资源，作为窗口里的操作界面。
2. Spring Boot 后端打成一个 Java 程序包，负责数据查询、保存、Excel 处理和分析计算。
3. Tauri/Rust 负责 Windows 桌面窗口、启动本地后端以及关窗时停止本地后端。
4. 使用 `jlink` 从 JDK 生成精简 Java 运行环境，随程序一起打包。
5. 将窗口程序、后端、运行环境和说明文件放入完整 ZIP，解压后运行 EXE。

所以，用户使用时不需要准备开发工具；开发人员重新编译桌面版时才需要 Node/pnpm、Java/Maven、Rust 和 Windows C++ 构建环境。

## 四、使用了哪些语言和技术

| 语言/工具 | 通俗解释 | 在项目里的工作 |
| --- | --- | --- |
| TypeScript / JavaScript | 写网页交互和数据传递的语言 | 驱动页面按钮、表格、筛选、导入和调用后端接口 |
| Vue 3 | 组织网页页面的框架 | 拼出基础信息、考试、成绩、分析等页面 |
| HTML / CSS / SCSS | 描述页面结构和外观 | 定义表格、弹窗、颜色、间距和响应式布局 |
| Element Plus | 一套现成的界面组件 | 提供按钮、表格、下拉框、对话框等常见控件 |
| ECharts | 图表工具 | 绘制成绩趋势、分布和对比图 |
| Java | 编写业务处理程序的语言 | 实现数据接口、成绩计算、Excel/PDF 报告和数据库操作 |
| Spring Boot | Java 后端框架 | 把 Java 业务组织成可供前端调用的本机接口 |
| SQL / SQLite | 数据查询语言和本地数据库 | 保存资料、考试、成绩及其关系；SQLite 不需要单独运行数据库服务器 |
| Rust / Tauri | 桌面窗口技术 | 生成 Windows EXE，管理窗口和本地服务的启动/退出 |
| PowerShell | Windows 自动化脚本 | 自动运行测试、编译后端、准备运行环境并制作发行 ZIP |
| Markdown | 纯文本说明格式 | 编写使用说明、需求、测试记录和开发进度 |

它们可以被理解成流水线：Vue 页面负责“看见和操作”，Java 后端负责“校验和计算”，SQLite 负责“保存数据”，Tauri/Rust 负责“把程序作为 Windows 窗口打开”，PowerShell 负责“把构建步骤自动化”。

## 五、开发环境需要准备什么

以下是**开发者构建项目**需要的工具，不是普通使用者的安装清单。

| 工具 | 用途 | 当前要求/说明 |
| --- | --- | --- |
| Windows 10/11 x64 | 编译和运行目标平台 | Windows 桌面版打包脚本只能在 Windows 执行 |
| Git | 下载源码和管理修改 | 用于克隆 GitHub 仓库、查看差异和提交代码 |
| Node.js | 运行前端开发和构建工具 | `frontend/package.json` 要求 Node.js 18 或更高版本 |
| pnpm | 安装前端依赖 | 按仓库锁文件安装，避免依赖版本漂移 |
| JDK 17 | 编译 Java 后端，也提供 `jlink` | 本地验证环境使用 Microsoft OpenJDK 17 |
| Maven 3 | 编译后端、运行测试和打包 JAR | 本地验证环境使用 Apache Maven 3.9.16 |
| Rust stable + Cargo | 编译 Tauri 窗口程序 | Windows 目标为 `x86_64-pc-windows-msvc` |
| Visual Studio C++ Build Tools | 给 Rust 程序提供 Windows 链接器和 SDK | 安装 C++ x64 工具与 Windows SDK 工作负载 |
| WebView2 Runtime | 显示窗口里的网页界面 | 用户电脑通常已有；缺少时需要安装微软运行时 |
| PowerShell 7（建议） | 执行项目构建脚本 | 示例命令使用 `pwsh`；Windows PowerShell 也可按本机情况调整 |

仓库脚本会优先使用 `.tools` 里的 JDK/Maven。该目录是开发机工具缓存，通常不提交到 GitHub；新开发电脑应按 README 或官方工具说明安装并校验。Rust、Visual Studio C++ Build Tools 和 WebView2 仍需本机准备。

### 在新电脑准备并启动开发版本

```powershell
git clone https://github.com/zheiseyummy/school-analysis-desktop.git
cd school-analysis-desktop
git checkout master

cd frontend
pnpm install --frozen-lockfile --ignore-scripts
cd ..
```

开两个 PowerShell 窗口：

窗口一启动本机后端：

```powershell
pwsh -NoProfile -File .\scripts\build-backend.ps1 -MavenArguments @('spring-boot:run')
```

窗口二启动前端：

```powershell
cd frontend
pnpm dev
```

开发页面地址为 `http://127.0.0.1:3000`，本地接口地址为 `http://127.0.0.1:8989`。这两个地址只供本机开发调试，用户日常用桌面 EXE 时不需要手动启动这两个窗口。

## 六、如何测试和判断是否可靠

测试不只看“页面能打开”，还要核对数据有没有串错、统计规则有没有误算、导出内容是不是对应正确的学生。

当前已做的检查包括：

1. **前端类型检查**：检查页面代码、接口字段是否存在明显类型错误。
2. **前端生产构建**：确认 Vue 页面可以生成可运行的静态资源。
3. **后端自动化测试**：当前后端有 32 项测试，覆盖计总分、缺考、未选科、正常 0 分、SQLite 初始化/升级、备份等核心规则。
4. **接口契约检查**：当前检查到 193 处本地导入、132 个前端 API 适配器、17 个后端控制器，报告 0 项契约错误。
5. **桌面打包与隔离启动**：2026-10-08 的 beta 包在隔离数据目录启动成功，学期 API 返回“上学期/下学期”，关闭窗口后本地服务退出。隔离数据测试没有改动用户真实数据库。
6. **虚拟报告测试**：用初高中不同科目数量的虚拟数据检查学生 Excel/PDF 的工作表、页数、动态科目、缺考和 0 分边界。

这些测试不能代替学校验收。特别是各校 Excel 的合并表头、列名、状态词和特殊成绩规则，必须拿脱敏后的真实样表进一步确认。

## 七、从 beta 到最终版还要做什么

“最终版”不只是把 EXE 编译出来，还必须证明真实业务规则正确并且数据安全。建议按以下顺序完成：

1. 收集并脱敏学校实际成绩表，验证不同学期、合并单元格、列名、缺考和未选科的导入结果。
2. 对照学校数据逐个核验学号、姓名、班级、考试、科目和学生成绩，确认报告没有错人。
3. 由学校确认综合素质评价表格格式、最终名单范围、比例和教师确认方式。
4. 取得高中正式赋分政策后，再明确计算群体、分段、边界和异常状态并测试；规则未确认前不启用赋分计算。
5. 在另一台干净的 Windows 10/11 电脑上测试：解压启动、WebView2、数据目录、导入导出、备份恢复和关闭退出。
6. 明确升级和旧数据迁移方法，完成最终备份/恢复演练；再决定是否制作正式安装包、签名和版本发布。

## 八、讲解时可以用的比喻

- **前端**像收银台和操作面板，负责让人看见数据并提交操作。
- **后端**像后台办事人员，检查输入、找到数据、计算统计并生成报告。
- **SQLite**像放在本机的账本，不需要单独租服务器。
- **Tauri 桌面窗口**像外面的包装盒，负责让整套程序变成 Windows 里可双击的应用。
- **测试**像正式交付前的对账：既检查每个环节能否运行，也核对学生和成绩是否一一对应。
- **1.1 beta**像试用样机：主要结构已经搭好，但必须用学校正式表格和另一台电脑做最后验收。

## 九、三分钟介绍稿

> 这个项目的目标是把成绩管理和分析做成个人 Windows 电脑上的本地桌面程序。我们先梳理原项目，把登录、权限、远程数据库等当前不需要的部分去掉，留下年级、班级、学生、教师、考试、成绩、分析、综合素质评价和备份功能。
>
> 技术上，界面使用 Vue 和 TypeScript，后端使用 Java 和 Spring Boot，数据用 SQLite 保存在本机，再由 Rust/Tauri 把系统包装成 Windows 窗口。普通使用者只要解压 ZIP、双击 EXE，不需要安装 Node、Java 或 Maven。开发人员才需要这些语言的编译环境和 Visual Studio C++ 工具。
>
> 目前已经做出 1.1 beta 便携版，跑过前端构建、32 项后端测试、接口检查和隔离数据库启动。系统也做了成绩状态区分、考试科目配置、个人 Excel/PDF 报告和综合素质评价。它还不是正式最终版，因为学校真实成绩表、正式赋分规则和其他电脑上的离线运行都需要继续验收。下一步会拿脱敏样表逐项对账，确认学生、考试、科目和报告都准确后，再定最终发布方式。
